# CampusMind · 校园多 Agent 应急协同决策平台

> 多个专业 AI 角色并行出方案，确定性规则引擎负责校验与裁决。
> **AI 只提议，程序负责判定与执行。**

![python](https://img.shields.io/badge/python-3.12-3776AB) ![tests](https://img.shields.io/badge/tests-125%20passed-brightgreen) ![mode](https://img.shields.io/badge/mock-可离线运行-blue)

## 1. 这是什么

校园突发事件（暴雨、火灾、停电、食物中毒）发生时，信息散落在不同部门，各部门目标不一致；而直接让大模型"接管调度"又不可信——单一的大模型调度可能会虚构不存在的车辆、封掉唯一的救援通道。

CampusMind 的做法是把"提议"和"裁决"拆开：

- **六个角色 Agent**（指挥 / 医疗 / 保卫 / 后勤 / 交通 / 学生事务）并行分析局势，各自只能输出一条结构化 JSON 建议；
- **规则引擎**逐条校验资源是否够、道路是否通、会不会切断别人的救援通道，并当场裁决冲突；
- **可选的决策 Agent（路线 B）** 站在全局视角重新编排方案，但同样要过规则引擎；
- 全过程在网页上**逐条浮现**，每次裁决、每次驳回、每次重申请都留痕。

## 3. 能做什么

### 3.1 四个应急场景

| 场景 | 事件 | 冲突演示点 |
| --- | --- | --- |
| `rainstorm` 暴雨内涝 | 积水断路、人员被困 | 校车争夺 + 封锁唯一通道 |
| `fire` 宿舍火灾 | 火势蔓延、消防通道占用 | 校车争夺 + 封路孤立 |
| `blackout` 大面积停电 | 电梯困人、照明失效 | 校车争夺 + 检修封路 |
| `food_safety` 食物中毒 | 病例扩散、医疗紧张 | 医疗包争抢 + 流调封控 |

### 3.2 演示时可调

| 参数 | 取值 | 作用 |
| --- | --- | --- |
| 事件等级 `severity` | 1–3 | 危险度与被困规模 |
| 人数规模 `scale` | 0.1–5 | 等比放大人口/被困/医疗需求 |
| 校车 `buses` / 冲锋舟 `boats` | 0–20 / 0–10 | 转运运力，直接决定冲突激烈程度 |
| 目标函数 `objective` | `rescue` / `fairness` / `economy` | 救人优先 / 区域公平 / 资源最省 |
| 轮次 `rounds` | 1–3 | 每轮之间态势恶化，重新决策 |
| 决策 Agent `decision_agent` | on / off | 路线 A（规则仲裁）↔ 路线 B（全局编排） |
| 地图 `map_id` | 上传后获得 | 使用自定义地图；留空用演示地图（见 §5） |

### 3.3 一次模拟发生了什么

```
事件生成 → 六角色并行分析 → JSON 契约校验 → 规则引擎裁决
        → 冲突拦截/降级 → 驳回后重申请（可选） → 执行并计算指标
        → 无干预对照 → 存档
```

前端按事件流逐步渲染：场景 → 每轮 → 每个角色 → 重申请 → 裁决 → 方案 → 指标。

## 4. 系统架构

```
┌──────────────── 浏览器（单页，无构建步骤） ────────────────┐
│ 场景/规模/目标函数/轮次控制 · SVG 态势图 · Agent 决策流      │
│ 冲突面板 · 可执行方案 · 路线 A/B 对比 · 无干预对照           │
└──────────────────────────┬─────────────────────────────────┘
                           │ SSE 事件流
┌──────────────────────────▼─────────────────────────────────┐
│ 调度中心 (FastAPI, 单异步 worker)                            │
│  ├─ Agent 层：六套提示词 + DeepSeek API + 契约校验 + 重试/降级│
│  ├─ 规则引擎：收益估算 · 资源校验 · 路径可达 · 冲突裁决       │
│  ├─ 决策 Agent（路线 B，可回退）                            │
│  └─ 模拟引擎：状态演进、方案执行、指标与基线                  │
└──────────────┬────────────────────────────┬────────────────┘
               │                            │
        SQLite（运行存档）           DeepSeek API（云端推理）
```

| 模块 | 职责 |
| --- | --- |
| `app/agents/` | 六角色提示词、DeepSeek 调用、契约校验、离线 mock、决策 Agent、调度 |
| `app/engine/` | 模拟状态（可达性/孤立检测）、规则引擎、方案执行与指标 |
| `app/data/` | 校园拓扑、场景注册表 |
| `app/storage.py` | SQLite 存档 |
| `app/static/` | 单页前端 |

### 4.1 六个角色

| Agent | 职责 | 允许的行动 |
| --- | --- | --- |
| 应急指挥 | 汇总信息、识别冲突、协调 | 广播、抢通、物资、待命 |
| 医疗 | 伤员、医疗包、医护力量 | 医疗支援、广播 |
| 保卫 | 道路封锁、疏散秩序 | 封路、疏散、广播 |
| 后勤 | 饮用水、食品、雨具 | 物资投送、广播 |
| 交通 | 车辆调度、救援路线 | 疏散、抢通、广播 |
| 学生事务 | 学生反馈、志愿者 | 疏散、广播 |

每个角色只允许在自己职责内行动（越权提议会被打回），并且调度中心会按"谁最该管哪片区域"分配重点区域，避免六个 Agent 全部涌向同一个区。

输出契约（模型必须逐字满足）：

```json
{
  "agent": "medical",
  "priority": "high",
  "target_area": "dorm_a",
  "action": "send_medical_team",
  "resource_required": {"medical_kits": 6, "volunteers": 4, "buses": 0, "boats": 0, "barricades": 0},
  "reason": "宿舍A被困 84 人，医疗需求最高"
}
```

### 4.2 规则引擎能拦住什么

| 能力 | 说明 |
| --- | --- |
| 资源不超发 | 按收益排序贪心分配，累计占用永不超过库存 |
| 路径可达 | BFS 判定医疗队/物资/疏散是否真能到达目标 |
| 孤立检测 | 封锁会让受困区域失去唯一通道时，直接降级为"设警戒点" |
| 冲突留痕 | 资源冲突、路径冲突、重复提议各有一条可读的裁决记录 |
| 去重合并 | 多个角色提同一行动时，保留优先级更高的一条 |
| 资源语义 | 广播通知不占用实体资源（模型挂了资源也会被忽略） |

### 4.3 两条决策路线

| | 路线 A · 规则仲裁（默认） | 路线 B · 决策 Agent |
| --- | --- | --- |
| 谁决策 | 收益排序 + 规则裁决 | LLM 全局编排，再交规则引擎校验 |
| 冲突处理 | 逐条拦截、按优先级取舍 | 提前避开冲突，冲突数显著更低 |
| 失败兜底 | 驳回角色带原因重申请 1 轮 | 校验失败带反馈重试，仍失败回退路线 A |
| 实测时延 | 6.5s（p95 8.0s） | 10.5s（p95 12.2s） |
| 实测冲突 | 平均 1.8 次 | 平均 0.6 次 |

### 4.4 目标函数

`score = 优先级×100 + 收益 − 目标函数调整`。目标函数只改变"同等条件下谁先上"，**不改变可行性判定**——超发资源、封断唯一通道这些硬约束在任何目标下都照样拦截。决策 Agent 会把目标函数写进提示词，作为编排依据。

### 4.5 多轮推演

每轮之间态势继续恶化（危险度 +0.6×等级、被困 +5%、医疗需求 +10%、志愿者 +4），六个角色在新局势下重新决策，指标按轮累计。

### 4.6 路线可视化

裁决通过后用 BFS 算出实际途经道路，随方案返回并在地图上画成流动虚线。地图上**每条道路都标注了名称**，因此方案里写的"2号道路""东环路"能直接在地图上对上；被某次提议点名时，道路及其标签会一起高亮。例如：

```
医疗支援 → 学生宿舍A：医务路 → 主干道 → 2号道路
物资投送 → 学生宿舍B：食堂路 → 北区路
```

## 5. 自定义地图（对外 API）

内置的 8 区域 / 11 条道路只是演示地图。**不传 `map_id` 时行为与之前完全一致**；传了就用外部拓扑。

### 5.1 地图就是一份 JSON

```json
{
  "name": "北校区",
  "zones": [
    {"id": "d1", "name": "一号宿舍", "kind": "residential", "x": 120, "y": 120, "population": 300},
    {"id": "t1", "name": "教学楼",   "kind": "dense",       "x": 320, "y": 160, "population": 260},
    {"id": "c1", "name": "医务点",   "kind": "medical",     "x": 420, "y": 300, "population": 10},
    {"id": "s1", "name": "体育馆",   "kind": "shelter",     "x": 520, "y": 420, "population": 20},
    {"id": "g1", "name": "校门",     "kind": "corridor",    "x": 120, "y": 420, "population": 40}
  ],
  "edges": [
    {"id": "r1", "a": "d1", "b": "t1", "name": "主路"},
    {"id": "r2", "a": "t1", "b": "c1", "name": "医务路"},
    {"id": "r3", "a": "t1", "b": "s1", "name": "避难通道"},
    {"id": "r4", "a": "d1", "b": "g1", "name": "环路"},
    {"id": "r5", "a": "g1", "b": "s1", "name": "南门路", "critical": true}
  ],
  "resources": {"buses": 3}
}
```

**区域 `kind` 决定它在场景中的角色**，不需要你指定谁是被困区：

| kind | 语义 | 用途 |
| --- | --- | --- |
| `residential` | 住宿区 | 优先成为受困区 |
| `dense` | 教学/办公密集区 | 次优先受困区；也可作为物资集散点 |
| `flow` | 人流区（食堂等） | 第三顺位受困区 |
| `medical` | 医疗点 | 医疗队出发点（必填，且唯一） |
| `shelter` | 避难所 | 疏散目标（至少一个） |
| `corridor` | 通道/校门 | 仅作通行节点 |

`critical: true` 表示该道路是重点通道，事件生成时会尽量保留它。

### 5.2 提交地图

```bash
curl -X POST http://127.0.0.1:8000/api/maps \
  -H "Content-Type: application/json" \
  -d @map.json
```

```json
{
  "map_id": "map-23a72157",
  "name": "北校区",
  "zones": 5,
  "edges": 5,
  "roles": {"medical": "c1", "shelters": ["s1"], "depot": "t1"}
}
```

校验失败返回 400，`detail.errors` 里是逐条原因：

```json
{"detail": {"message": "地图校验失败", "errors": ["至少需要一个 kind=medical 的区域（医疗队出发点）"]}}
```

校验规则：

| 规则 | 说明 |
| --- | --- |
| id 格式 | `[A-Za-z0-9_-]{1,32}`，区域内/道路内不得重复 |
| 规模 | 3–40 个区域，≤80 条道路 |
| 引用完整 | 道路两端必须是已声明的区域，且不能自环、不能重复连接同一对区域 |
| 语义完整 | 至少一个 `medical`、一个 `shelter`、一个可受困区域（`residential`/`dense`/`flow`） |
| 资源 | 键只能是 `medical_kits`/`volunteers`/`buses`/`boats`/`barricades`，值为非负整数；未写的项用默认值 |

### 5.3 用自定义地图跑模拟

所有模拟接口都接受 `map_id`，其余参数不变：

```bash
curl -X POST "http://127.0.0.1:8000/api/simulate?map_id=map-23a72157&scenario=fire&seed=7"
curl "http://127.0.0.1:8000/api/simulate/stream?map_id=map-23a72157&rounds=2"
curl "http://127.0.0.1:8000/api/scenario?map_id=map-23a72157&severity=3"
```

`scenario` / `result` 事件都会回显 `map_id`；未知 id 返回 **404**。网页上的「地图 ID」输入框留空即用演示地图。

### 5.4 事件如何落到你的地图上

不需要你手写"哪里淹水"，系统按 `kind` 自动生成：

1. 按 `residential → dense → flow` 顺序选出最多 3 个受困区，人数按场景画像分配；
2. 危险度按场景类型落在受困区（积水/火势/影响/病例密度），其余区域保持低危险度；
3. 如果是 Ⅱ 级以上事件，会**封闭部分道路来制造"唯一通道"**，但有一条硬约束：**封闭后每个受困区必须仍能到达所有救治点**，否则不封——避免自定义地图被生成成死局；
4. 角色（医疗点 / 避难所 / 物资集散点）由 `kind` 自动推导，规则引擎与前端无需改动。

## 6. 实测效果（live 模式，seed=7，1 轮）


| 场景 | 受困 | 转移 | 医疗处置 | 物资覆盖 | 覆盖率 | 冲突拦截 | 无干预预计伤亡 | 风险覆盖 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 暴雨内涝 | 229 | 50 | 23 | 80 | 26.9% | 2 | 17 | 100% |
| 宿舍火灾 | 220 | 50 | 10 | 80 | 25.0% | 2 | 26 | 94.5% |
| 大面积停电 | 130 | 50 | 11 | 80 | 42.7% | 2 | 15 | 100% |
| 食物中毒 | 200 | 50 | 28 | 0 | 32.0% | 0–2 | 23 | 95.1% |

**冲突示例（暴雨，保卫要求封锁 2 号道路）**

> 封锁 2 号道路将切断被困区域的唯一救援通道
> 裁决：不中断通行，改为设警戒点并由保卫科现场疏导

**反事实对照**：不做任何调度时，30 分钟内 91 人陷入危险、预计 26 人伤亡；本方案转移 50 人、医疗处置 22 人，风险覆盖 94.5%。

> 覆盖率偏低是因为全校只有 2 辆校车（单轮最多转移 50 人）——这是资源约束下的真实结果，不是调度的失败。把 `buses` 调到 6，同样场景可转移 150 人。

数据由 `scripts/benchmark.py` 生成，可复现（见 §7.5）。

## 7. 工程成熟度（实测，非估算）

### 7.1 时延与成功率

| 场景 | 平均 | p95 | 成功率 |
| --- | --- | --- | --- |
| 离线 mock（10 seeds） | 0.01s | 0.01s | 100% |
| live 路线 A（5 seeds） | 6.46s | 8.00s | 100% |
| live 路线 B（5 seeds） | 10.46s | 12.16s | 100%（回退率 20%） |
| 8 路并发（live 路线 A） | 23.65s | 25.38s | 100% |

8 路并发的时延不是 8×6.5s——因为全局 AI 并发上限是 4，请求会排队；成功率高说明是在等待而不是失败。演示场景（1–3 位评委）用不到这个并发量。

### 7.2 故障与降级路径

| 故障 | 处理 |
| --- | --- |
| 模型输出不是合法 JSON | 带错误反馈重试 1 次；仍失败则该角色本轮待命 |
| 模型把区域填进道路字段 | 契约层识别并带反馈重试，不进入裁决 |
| 角色越权（学生事务申请医疗队） | 直接打回并告知允许的行动集合 |
| 决策 Agent 返回裸对象 / 空方案 | 归一化兼容 + 要求至少 3 项，否则重试，仍失败回退路线 A |
| DeepSeek 超时 / 网络错误 | 单角色降级，不影响整轮；异常写入该角色的理由 |

### 7.3 单 worker 的依据

2 核 2GB 上**不用 gunicorn 多 worker**，原因是正确性而不是性能：

1. 模拟状态在进程内存里，多 worker 会状态分叉；
2. SSE 长连接会被钉在单个 worker 上；
3. 全局 AI 并发上限需要共享信号量，多进程无法保证；
4. SQLite 并发写需要额外处理；
5. 峰值叠加易触发 OOM，演示现场最怕。

真正的并发能力来自异步 I/O：单 worker 下 8 路并发请求全部成功（见 §7.1）。

### 7.4 成本

每次模拟约 11.3k 字符输入（六套提示词）+ 1.3k 字符输出，按中文与 JSON 的常见折算约 **7–8k token/次**。以 deepseek-chat 官方定价估算，单次运行成本在**分级钱**量级；跑 100 次演示的消耗可忽略，但不要写死循环压测。

### 7.5 复现

```powershell
uv run python -m scripts.benchmark --seeds 10 --mode mock      # 离线基线
uv run python -m scripts.benchmark --seeds 5  --mode live --decision
uv run python -m scripts.benchmark --seeds 0 --http-concurrency 8
```

## 11. 设计取舍

- **六个角色共用一个模型**：不是六台服务器、六个模型，靠提示词区分角色。省成本、省显存，代价是角色边界必须由程序约束（见 §4.1）。
- **规则引擎而不是让 LLM 自检**：确定性、可复现、可测试，且能回答"AI 说错了你们怎么发现"。
- **SQLite 而不是 Redis/Postgres**：单机、单 worker、演示级数据量，多一个服务只是多一个故障点。
- **前端零构建**：单页 HTML + 原生 JS，`uv run` 即可演示，不需要 node 工具链。
- **不追求"完美方案"**：覆盖率受运力限制是真实的，把限制显示出来比藏起来更可信。

## 12. 已知限制

- 运力约束下覆盖率只有 25%–43%，提升依赖调参而非算法；
- 各场景冲突密度不均，食物中毒最"安静"（无孤立通道）；
- 多轮 + 决策 Agent 组合约 20s，演示建议二选一；
- 决策 Agent 在约束更紧的第 2 轮有约 20% 回退率；
- 自定义地图只校验结构与语义，**不校验可行性之外的合理性**（比如把避难所画在校门外）；
- 地图接口暂无删除/覆盖，只能新增；也没有鉴权，定位是演示原型；
- 无鉴权、无限流、无多会话隔离，定位是演示原型而非生产系统。
