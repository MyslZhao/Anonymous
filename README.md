# CampusMind — 校园多 Agent 应急协同决策平台

> Hackathon 参赛项目 · 两天 MVP · 团队 2–3 人

## 1. 一句话定位

CampusMind 不是聊天机器人，而是一个**可以模拟校园突发事件、让多个专业 AI 角色协作、由程序校验资源冲突并产出可执行应急方案**的决策演示系统。

核心设计原则，全文一切决策都由它推导：

> **AI 负责提出方案，程序负责计算与裁决。**

Agent 只输出结构化建议，资源够不够、道路通不通、行动冲不冲突，一律由**规则引擎**判定后执行。这既挡住模型幻觉，也是 2GB 内存能跑得动的根本原因。

## 2. 演示场景

### 2.1 模拟校园

不使用真实地图 API，不做 3D 建模，用 SVG 平面图。共 8 个区域：

| 区域 | 属性 |
| --- | --- |
| 教学楼 | 人员密集 |
| 学生宿舍 A | 居民密集 |
| 学生宿舍 B | 居民密集 |
| 食堂 | 人员流动大 |
| 医务室 | 医疗资源 |
| 图书馆 | 人员密集 |
| 体育馆 | 临时避难点 |
| 校门及道路 | 救援通道 |

每区固定基础数据：人口数量、危险度（积水/火势/影响/病例密度）、风险等级、道路状态、医疗需求、物资需求。全部为自建模拟数据，不接入任何真实校园隐私信息。

### 2.2 应急场景

同一套校园拓扑上挂 4 个突发事件，规则引擎与六个 Agent 角色完全复用：

| 场景 id | 名称 | 冲突演示点 | 关键约束 |
| --- | --- | --- | --- |
| `rainstorm` | 暴雨内涝 | 校车争夺 + 封锁唯一通道 | 积水断路，医疗包 14 |
| `fire` | 宿舍火灾 | 校车争夺 + 消防通道封闭 | 医疗需求高（50%），医疗包 10 |
| `blackout` | 大面积停电 | 校车争夺 + 检修封路 | 滞留多、医疗需求低，志愿者 40 |
| `food_safety` | 食物中毒 | 校车争夺 + 流调封控唯一通道 | 医疗包仅 6，需求 80% |

模拟规模：每场景 100–500 人（**程序模拟数据，不是 500 个 LLM Agent**）、同时模拟任务 1–2 个。

**演示时可即时调整**（不改代码）：

| 参数 | API | 页面 | 说明 |
| --- | --- | --- | --- |
| 人数规模 | `scale` 0.1–5.0 | 0.5×–3× 下拉 | 等比放大人口、被困人数、医疗需求与物资需求 |
| 校车数 | `buses` 0–20 | 输入框（留空用场景默认） | 转运主运力，直接改变资源冲突的激烈程度 |
| 冲锋舟数 | `boats` 0–10 | 输入框（留空用场景默认） | 涉水救援运力 |

把人数调大、把运力调小，冲突会更早爆发，适合演示"AI 如何取舍"；反过来则演示"资源充足时如何统筹"。

新增场景只需在 `app/data/scenarios.py` 写一个 `_build_xxx(seed, severity)` 并注册进 `SCENARIOS`，前端下拉框与 API 自动识别，无需改动规则引擎。

## 3. 架构

### 3.1 分层

```
前端 Web（Vue 3 + Vite）
  场景设置 · 校园地图 · Agent 面板 · 数据图表 · 结果对比
        │
后端调度中心（FastAPI）
  接收事件 · 组织 Agent · 管理模拟轮次 · 校验结果
        ├── Agent 决策层 → DeepSeek API（六套角色提示词，同一个模型）
        ├── 规则模拟引擎 → 资源/人数/库存/时间/行动结果
        └── SQLite → 事件、Agent 决策、模拟结果、方案对比、报告
```

技术栈（刻意做减法）：

| 部分 | 技术 | 理由 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite + Element Plus | 快速搭建管理后台 |
| 图表 | ECharts | 模拟数据与方案对比 |
| 地图 | 静态 SVG 平面图 | 不做真实地图系统 |
| 后端 | Python + FastAPI | 适合写模拟规则与 AI 调度 |
| AI | DeepSeek API | 复杂决策与分析 |
| 存储 | SQLite（Docker Volume 持久化） | MVP 不需要独立数据库服务 |
| 部署 | Docker Compose + Nginx + FastAPI 双容器 | 单机多服务最省事的组织方式 |

### 3.2 部署

- **开发端**：Windows，本地构建前端，只上传 `dist` 静态文件。
- **运行端**：阿里云 ECS，Alibaba Cloud Linux / 2 核 / 2GB RAM / 2GB Swap / Docker 已装。
- **容器**：`nginx`（静态资源 + 反向代理）、`fastapi`（模拟引擎 + Agent 调度 + 规则引擎）。
- **模型**：全部走云端 DeepSeek API，**服务器上不跑模型**。

## 4. Agent 设计

### 4.1 六个角色（原型阶段固定为 6 个）

| Agent | 职责 |
| --- | --- |
| 应急指挥 | 汇总信息、识别冲突、提出整体协调方案 |
| 医疗 | 伤员、医疗需求、医疗包与救护车分配 |
| 保卫 | 道路封锁、人员疏散、安全区域判断 |
| 后勤 | 饮用水、食品、雨具、救援物资调配 |
| 交通 | 道路通行情况、车辆路线、救援路径规划 |
| 学生事务 | 学生反馈、人员需求、志愿者组织 |

六个角色共用同一个 DeepSeek 模型，仅通过六套角色提示词区分，**不需要六台服务器，也不需要六个独立模型**。

**调度中心会给每个角色分配"本轮重点区域"**（交通→被困最多、学生事务→第二多、医疗→医疗需求最高、保卫→危险度最高、后勤→剩余区域中人口最多），作为提示词的一部分传下去。六个 Agent 并行、互相看不到对方输出，如果不做分工，模型会全部涌向同一个区域，演示就会退化成"六个人抢一件事"。分工只是建议，最终是否采纳仍由 Agent 决定，规则引擎照旧校验。

> 决定：先按 6 个 Agent 开发原型评估效果，后续**根据实际运行效果再增减**（例如观测某个角色输出长期被忽略，或某两个角色职责重叠则合并）。角色数量是实验变量，不是先验设定。

### 4.2 输出契约

每个 Agent 必须输出结构化 JSON，不接受纯自然语言：

```json
{
  "agent": "medical",
  "priority": "high",
  "target_area": "宿舍A",
  "action": "send_medical_team",
  "resource_required": { "medical_kits": 5, "volunteers": 3 },
  "reason": "该区域医疗需求较高"
}
```

后端解析失败要能降级（重试一次 → 该角色本轮弃权），不能让一个角色的坏输出拖垮整轮模拟。

### 4.3 协作与冲突裁决（方案待定，实验性）

一次性让六个角色各说一句，不构成"协作"。当前排除了"六 Agent 自由聊天"（Token 与时延都不可控，且难以验收），保留两条候选路线：

- **路线 A（默认）**：规则引擎仲裁。六份建议汇总后，由规则引擎检测资源冲突与路径冲突，冲突项按优先级/资源占用顺序裁决。
- **路线 B（实验性，feature flag，默认关闭）**：**独立的"决策 Agent"**。它接收六份结构化提议 + 当前资源快照，以**利益最大化**为目标函数（如：受困人员覆盖数最大、平均响应时间最小、资源代价最低）产出整体调度方案，再交由规则引擎校验；校验不通过则带失败原因回环重试，最多 N 轮。

实现要求：路线 B 作为可开关模块存在，**默认关闭**，用于原型阶段与路线 A 做同一场景的对比评估。开关状态与评估结论记录在此文档。

**live 实测暴露的两个坑，已修**：

1. 模型有时不按 schema 输出，直接把**单个行动对象**当顶层返回（没有 `plan` 数组）。原实现会判"空方案"并立即回退路线 A——8 次实测里有 4 次。现在 `normalize_plan()` 兼容 `plan / actions / decisions / plan_items`、裸对象、映射结构、中文枚举，并对单条非法项做丢弃而非整份失败。
2. 即使能解析，只返回 1 项行动也不算"决策"。现在要求 **至少 3 项、覆盖多个部门**，否则带着"方案不完整"的反馈重试；重试仍失败才回退路线 A（回退时前端会显示完整轨迹，不会静默降级）。

修复后 8 次实测：**0 次回退**，方案项数 4–6。

**路线 A 也补齐了对等能力（否则 A/B 不公平）**：被规则引擎驳回的角色，会带着"你上一条建议为什么被驳回"重新申请，最多 `ROUTE_A_RETRY` 轮（默认 1，环境变量可调）。重申请有两个约束，防止变成刷分：

- 新版建议与旧版**完全相同就跳过**，不空转（所以 mock 模式永远不会触发重申请）；
- 新版建议必须仍在**角色边界内**（学生事务不能申请医疗队、后勤不能封路），越权会被打回。

前端会给重申请过的角色打上"已重申请"标签，并显示驳回原因与新版行动，过程完全可见。

### 4.4 目标函数（可调，对应"智能调度"的价值观）

同一场事故、同样的资源，不同的取舍会产出完全不同的方案。目标函数把这件事从"模型内部的黑箱"变成可切换的演示项：

| id | 名称 | 排序偏好 |
| --- | --- | --- |
| `rescue` | 救人优先 | 收益最大化，资源消耗只是轻微代价（默认） |
| `fairness` | 区域公平 | 同一区域被多个角色盯上时降权，鼓励把资源铺开 |
| `economy` | 资源最省 | 明显提高资源代价权重，优先低成本行动 |

实现方式：`score = 优先级权重×100 + 收益 - 目标函数调整`。目标函数**只改变"同等条件下谁先上"，不改变可行性判定**——无论选哪个目标，资源超发、道路阻断这些硬约束照样拦截。决策 Agent（路线 B）会把目标函数写进提示词，作为其编排依据；它的产出同样要过规则校验。

### 4.5 多轮推演（时间推进）

一轮结束不代表事故结束。`rounds` 参数支持 1–3 轮，每轮之间态势继续恶化：

- 仍被困区域危险度 +0.6×事件等级，被困人数 +5%，医疗需求 +10%；
- 志愿者少量补充（+4），校车、医疗包不恢复。

六个角色在**变化后的态势**上重新分析、重新决策，因此"第 2 轮"不是重复播放，而是"情况变糟了，再调度一次"。指标按轮累计，前端按轮次打标签（R1/R2）。

### 4.6 路线可视化

规则引擎裁决通过后，会顺带用 BFS 算出该行动的**实际途经道路**（医疗队从医务室出发、物资从教学楼集散点出发、疏散到最近的避难所），随方案一起返回。前端把这些道路序列画成地图上的流动虚线——评委看到的不是"转移 50 人"，而是"经 2 号道路 → 东环路进入体育馆"。

## 5. 演示规范（Demo Spec）

以下两条是**硬性要求**，不是加分项。

### 5.1 必须人为构造一个资源冲突

演示中要能当场看到"Agent 之间意见真的打架，且系统真的解决了它"。推荐冲突设计：

- 医疗要 2 号道路送人，保卫要封锁 2 号道路；
- 后勤全校区只有 2 辆校车，但宿舍 A 和宿舍 B 同时申请。

规则引擎必须判定冲突 → 输出冲突提示 → 由指挥 Agent（或路线 B 的决策 Agent）重新分配资源 → 给出可执行方案。这比六个角色各说一句，强十倍地证明"多 Agent 真在协作"。

### 5.2 过程必须可见

前端采用**逐步揭示**（streaming / 分步渲染）：事件触发 → 各 Agent 分析中 → 建议逐条出现 → 冲突高亮 → 最终方案。

禁止把全部结果攒完后一次性渲染。演示时必须让人看到"决策过程"，同时掩盖 API 累计时延（建议单次模拟总耗时控制在演示可接受范围内，超过则前端先出模拟引擎的中间态）。

## 6. 运行参数与并发评估

### 6.1 并发模型结论：不要上 gunicorn 4 worker

**结论：在 2 核 2GB + 2GB Swap 上使用 gunicorn 4 worker 大概率不可行，不建议采用。**

理由（按严重程度排序）：

1. **进程各自持有一份内存状态。** 4 个 worker = 4 个独立 Python 进程，模拟引擎的居民/区域/资源状态不共享。同一场模拟的请求被负载均衡到不同 worker，状态就会分叉——这是正确性问题，不是性能问题。要修就得把状态外置到 SQLite/Redis，而 Redis 已在禁用清单里。
2. **长连接会把 worker 占死。** 演示依赖逐步揭示（SSE/WebSocket），长连接被固定在某一个 worker 上。gunicorn 若用 sync worker，4 个并发长连接就能把服务打满；必须用 `uvicorn.workers.UvicornWorker`（异步）才有意义。
3. **全局并发限流失效。** "同时最多 3–5 个 AI 请求"这一约束是全局的，多进程下无法靠进程内信号量保证，需要共享锁（又要 Redis）。
4. **内存与 OOM 风险。** 2GB 扣除系统 350–550MB、Nginx 20–50MB 后约 1.3–1.4GB 可用；FastAPI 单 worker 规划 150–350MB，4 worker 在峰值叠加模拟数据后极易触发 OOM killer 无差别杀进程——演示现场最怕的事故。
5. **SQLite 写锁竞争。** 4 个进程并发写同一份 SQLite，未开 WAL 时会出现 `database is locked`。

**推荐配置：1 个异步 worker（`uvicorn` 单进程 + async I/O），用 `asyncio.Semaphore(3~5)` 做全局 AI 调用限流。**
真正的并发能力来自异步 I/O，不来自进程数。评委只有几位，前端并发个位数，单 worker 足够。

**允许升级的条件**（满足全部才考虑加到 2 worker）：实测 `docker stats`/`free -h` 显示 CPU 打满、内存仍有 ≥400MB 余量、且模拟状态已全部外置到存储层。硬性上限 2，不做 4。

### 6.2 资源预算（规划值，非实测）

| 服务 | 预算 |
| --- | --- |
| Linux 系统及基础服务 | 350–550MB |
| Nginx | 20–50MB |
| FastAPI（单 worker） | 150–350MB |
| SQLite | 视数据量，通常较小 |
| 其他与运行余量 | 预留 300–500MB |

Swap 只兜偶发峰值，**不能当内存扩容手段**，也不作为增加 Agent 数量的依据。

## 7. 非目标与禁用清单

避免两天内把时间烧在基础设施上。以下明确不做：

- 微服务、Kubernetes、消息队列
- Redis、PostgreSQL、向量数据库
- PyTorch / Transformers，或在 ECS 上部署本地大模型
- 真实地图 API、3D 建模、真实校园隐私数据
- 在服务器上执行前端构建（一律本地构建后上传）
- FastAPI 多 worker（见 6.1）
- 六个 Agent 自由多轮聊天

**M2（Day2 18:30）验收标准**：公网可访问的演示环境 + 3 分钟演示脚本 + 兜底录屏。

### 9.4 砍需求的顺序（提前定死，避免现场争吵）

1. 先砍 ECharts 方案对比与报告导出（用表格代替）。
2. 再砍决策 Agent 路线 B（回退路线 A，README 已有开关）。
3. 最后才砍模拟居民规模（500 → 100，拓扑不变）。
4. **永不砍**：一次完整模拟闭环、冲突检测与重分配、过程可见。

## 10. 本地原型（当前可运行）

单机、单进程、零外部依赖即可跑通「事件 → 六 Agent 建议 → 规则裁决 → 方案 → 指标 → 存档」。

### 10.1 启动

依赖统一由 [uv](https://docs.astral.sh/uv/) 管理，项目用 `.python-version` 锁定 Python 3.12，**uv 会自己准备解释器，与系统里装了什么版本无关**。

```powershell
uv sync                          # 按 uv.lock 安装依赖并准备 Python 3.12
Copy-Item .env.example .env      # 不填 Key 则自动进入离线 mock 模式
uv run python run.py             # 打开 http://127.0.0.1:8000
```

打开 <http://127.0.0.1:8000>。页面右上角徽标会显示「离线模拟模式（Mock）」或「在线模式 · deepseek-chat」。

- **不填 `DEEPSEEK_API_KEY`**：六角色建议由本地规则生成，形态与真实返回完全一致，可完整演示与测试。
- **填了 Key**：走真实 DeepSeek 调用，同样必须通过 JSON 契约校验，不合格会重试一次，仍失败则该角色本轮降级为无建议。
- 推理服务不本地运行，符合 §6.1 的轻量化约束。

### 10.2 页面能力

- 顶部可切换**应急场景**、事件等级、随机种子、人数规模、校车数、冲锋舟数、**目标函数**与**推演轮次**。
- 左侧：突发事件、可用资源、SVG 校园态势图（危险度填充 / 阻断道路 / 待救区域 / **行动路线**）、执行效果、**无干预对照**。
- 右侧：六角色建议**逐条浮现**（点目标区域地图会高亮）、冲突与裁决、可执行方案（含被驳回原因）、路线 A/B 对比表。
- 被驳回的角色重申请后，卡片会打上"已重申请"标签并换成新行动；多轮时每轮重置卡片并显示轮次。
- 勾选「决策 Agent（路线 B）」后，同一场景会同时算出 A、B 两套方案并给出对比。
- 地图与指标的措辞随场景切换（积水 / 火势 / 影响 / 病例密度，被困 / 滞留 / 待救治）。

**无干预对照（反事实基线）**：不做任何调度时的 30 分钟推演，用于回答"AI 到底避免了什么"。

```
风险暴露 = 被困人数 × (0.15 + 0.35 × 危险度/10)
预计伤亡 = 被困人数 × (0.03 + 0.12 × 危险度/10)
失去通道的区域，暴露系数 × 1.15
```

页面上与"本方案转移 / 医疗处置 / 物资覆盖"并排展示，并给出**风险覆盖率**。这是粗粒度对照模型，不是真实伤亡预测，卡片上也会写明这一点——评委追问时要能立刻承认边界，而不是把模拟值当结论。

## 11. 服务器部署（uv）

### 11.1 为什么不再用系统 Python

ECS 自带 Python 3.6，装不了任何现代依赖：`pydantic-core` 等包早就不再发布 3.6 的 wheel，`pip install` 必然失败；硬装源码还要 Rust 工具链和编译内存，2C2G 上大概率 OOM。

结论：**不要动系统 Python，也不要试图升级它**（Alibaba Cloud Linux 的系统包管理器会牵一发动全身）。用 uv 自带解释器，与系统 3.6 完全隔离。

### 11.2 方案 A：服务器能访问外网（推荐）

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"

uv python install 3.12        # uv 自己下载 CPython，不需要系统 Python
uv sync --frozen --no-dev     # 按 uv.lock 安装，版本与本地完全一致
uv run python run.py --host 0.0.0.0 --port 8000
```

国内网络慢的话，先设镜像再执行：

```bash
export UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
export UV_PYTHON_INSTALL_MIRROR=https://ghproxy.net/https://github.com/astral-sh/python-build-standalone/releases/download
```

服务启动后 `curl http://127.0.0.1:8000/api/health` 应返回 `{"status":"ok",...}`。首次启动会建 `data/campusmind.db`，记得把这个目录挂到持久化位置。

### 11.3 方案 B：服务器完全无法访问外网

1. 本地生成离线包（Linux x86_64 / CPython 3.12 的 wheel，在 Windows 上也能打包）：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts\make-wheelhouse.ps1 -Out wheelhouse
   ```

2. 把 `wheelhouse/`（含自动生成的 `requirements.txt`）、`uv.lock`、`pyproject.toml`、`app/`、`run.py` 一起上传。

3. 服务器上（`uv` 二进制可从本地下载后一并上传，它是单文件静态程序）：

   ```bash
   uv venv --python 3.12 .venv      # 若连解释器都下不了，见下方备注
   uv pip install --no-index --find-links wheelhouse -r wheelhouse/requirements.txt
   .venv/bin/python run.py --host 0.0.0.0 --port 8000
   ```

   > 备注：如果服务器连 CPython 都下载不了，就在**任意联网的 Linux 机器**上执行 `uv python install 3.12`，
   > 把 `~/.local/share/uv/python/` 整个目录打包上传，再用 `uv venv --python <该目录下的 python3.12>` 指定解释器。

### 11.4 服务器上的并发

`run.py` 直接用 uvicorn 单进程启动，就是 §6.1 的结论：**单异步 worker**。不要在服务器上套 gunicorn 开多 worker——模拟状态在进程内存里，多 worker 会导致状态分叉。

上线后按 README §6.1 的闸门实测：

```bash
free -h && docker stats --no-stream 2>/dev/null; ps -o rss= -p $(pgrep -f "run.py" | head -1)
```
